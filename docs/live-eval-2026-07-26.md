## Failure Analysis

The raw categories were four `model_planning_error`, three `max_turns`, and one
`tool_error`. Trace review found two evaluation-validity issues behind those labels.

Five attempts produced correct files, passed tests, and completed normally, but used
`write_file` instead of `edit_file`. The rubric required one exact implementation tool, so
these attempts failed even though the user-visible task succeeded. This is useful as a
tool-policy conformance metric, but it should not be called task correctness.

All three `list_boundary` attempts fixed the requested bug and ended with passing tests. The
fixture used `T | None`, while the shell resolved `python3` to Python 3.9; that annotation is
evaluated at import time and fails on Python 3.9. The model detected and repaired this
environment issue, but the final successful test command consumed turn 8, leaving no turn for
a completion response. These are legitimate runtime termination failures, but the fixture
did not isolate the intended off-by-one behavior.

The single raw `tool_error` label is also misleading: `missing_path_recovery` deliberately
expects its first `read_file` call to fail. The run satisfied that recovery assertion and its
tests; only the exact `edit_file` assertion failed. Failure classification should distinguish
expected tool errors from unexpected ones.

## Interpretation

The strict 46.7% score is the reproducible result for the original rubric and must remain the
headline when discussing that exact run. The 80.0% completion score and 100.0% final-workspace
correctness are diagnostic slices, not replacements for the original metric.

This run demonstrates that the live provider path, native function tools, policy layer,
workspace tools, multi-turn continuation, trace capture, usage accounting, and incremental
reporting all worked without provider failures. It also demonstrates why an eval harness
needs rubric validation and environment pinning in addition to more samples.

## Next Improvements

1. Separate artifact correctness, runtime completion, and tool-policy conformance into
   independent metrics.
2. Pin the fixture interpreter or run tests with the Harness environment's Python executable.
3. Treat expected tool failures as successful recovery signals during failure classification.
4. Calibrate turn budgets from observed traces and report success-at-turn-budget curves.
5. Repeat the same fixed suite before comparing models or claiming an improvement.
